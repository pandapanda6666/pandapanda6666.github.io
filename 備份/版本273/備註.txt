### 關鍵根因剖析（讀檔與存檔盲區）

1. **後端 Session 憑證只存記憶體，完全沒有「存檔與讀檔」（致命傷）：**
   - **存檔缺失**：原本伺服器登入產生的 Token 僅暫存在 Node.js 執行階段的 `sessionTokens = new Map()` 中，**從未寫入資料庫硬碟檔 (`系統紀錄.txt`)**。
   - **讀檔缺失**：伺服器每次重新啟動或重載時，`loadDB()` **完全沒有去讀取先前的憑證**。
   - **後果**：伺服器一旦關閉重啟，所有使用者的 Token 瞬間消失歸零。前端開啟時發送 `tokenLogin`，後端查無此 Token，直接回傳「登入已過期或失效」，強制使用者重新登入。

2. **前端密碼存檔存成 `undefined`（存檔 Bug）：**
   - 前端 `login-hub` 原先在登入後嘗試執行 `localStorage.setItem('panda_auto_pass', res.password)`。
   - 但基於安全性考量，伺服器回傳的 `loginResult` 根本沒有包含 `password` 欄位（值為 `undefined`），導致一般登入密碼存成字串 `"undefined"`，且 Google 登入也未標記 `'GOOGLE_AUTH'`。
   - 當 Token 驗證失敗時，前端本應自動嘗試以記憶的帳密平滑復原，卻因密碼是 `undefined` 而直接崩潰踢出。

3. **管理面板完全漏讀 Token（讀檔 Bug）：**
   - 遠端管理面板 `settings.html` 在 Socket 連線後，**根本沒有去讀取 `panda_session_token`**，只讀取 `panda_auto_pass`。
   - 加上上述密碼為空的連鎖效應，管理頁面一開啟就被判定為未授權，立刻彈窗強制跳轉回登入中心。
   - 從登入中心跳轉回管理面板時，URL 帶有 `?token=...`，但管理面板連線時並未解析 URL 參數儲存。

---

### 全面修復措施

1. **伺服器端（憑證永久持久化＋安全讀存）：**
   - **開機讀檔**：在 `loadDB()` 加入 `db.sessionTokens` 反序列化機制，伺服器重啟時自動還原所有使用者的登入 Session。
   - **安全存檔**：在 `saveDB()` 自動將記憶體中所有有效 `sessionTokens` 同步寫入 `系統紀錄.txt`；在一般登入、Google 登入生成 Token 時立即寫入存檔；主動登出時同步銷毀。
   - **安全登入防護**：`tokenLogin` 新增 `oldSocket.id !== socket.id` 防自身踢除機制，並在憑證無效時回傳 `tokenFailed: true` 供前端精準辨識。

2. **前端登入中心（密碼存檔與平滑復原）：**
   - 修復密碼儲存邏輯：Google 登入自動標記 `'GOOGLE_AUTH'`，一般登入則正確保存已驗證輸入的密碼。
   - 新增無感平滑降級重登：當 Token 因任何極端情況過期時，前端不再粗暴彈窗踢人，而是自動以 Google Firebase Auth 或已記憶的帳密在背景秒速重新認證換發新 Token。

3. **遠端管理面板（雙端同步修復讀檔）：**
   - `settings.html` 與 `index.html` 在連線前優先讀取並保存 URL 傳遞之 `token` 與 `user` 參數。
   - 建立 `panda_session_token` -> `GOOGLE_AUTH` -> `panda_auto_pass` 三級優先驗證機制。
   - 驗證成功後立即將最新 Token 與使用者名稱持久化至本地 `localStorage`，確保後續重開管理面板順暢開啟。
4.1. 於 server.js 的 loadDB 與 saveDB 實裝 sessionTokens 憑證磁碟持久化，解決伺服器重啟憑證歸零問題。
2. 於 login-hub/index.html 修復密碼儲存與 Google 授權標記，新增 Token 過期時自動降級重登機制。
3. 於遠端管理面板 settings.html 與 index.html 補齊 panda_session_token 讀取、URL token 參數解析與驗證成功後之憑證持久化存檔。
4. 建立後端版本199備份與 GitHub 倉庫版本273備份，更新完整對話紀錄與 Rule 8 對話紀錄，並推送代碼至 GitHub。
